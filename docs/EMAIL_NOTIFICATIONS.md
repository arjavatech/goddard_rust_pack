# Transactional Email Notifications

Authoritative spec for the parent-facing transactional emails fired by the Goddard backend.
Implementation lives in `lambda/goddard/src/services/email_service.rs`,
`lambda/goddard/src/services/email_templates.rs`, and `lambda/goddard/src/models/email.rs`.

## Overview

Six lifecycle events trigger emails to parents. The original API responses are never blocked by
email delivery (fire-and-forget via `tokio::spawn`). Resend is the upstream provider; the same
account that already sends form-reminder emails.

| # | Event | Backend trigger (existing) | Recipient(s) |
|---|-------|----------------------------|--------------|
| 1 | Admin approves a form | `POST /student-form-assignments/review` (status=approved) | Primary parent + secondary parent (if set) |
| 2 | Admin rejects a form  | `POST /student-form-assignments/review` (status=rejected) | Primary parent + secondary parent (if set) |
| 3 | Admin adds an additional child | `POST /enrollments/add-child` | The owning parent |
| 4 | Admin deactivates a parent | `DELETE /parent/:parent_id` | The deactivated parent |
| 5 | Admin archives a child | `PATCH /children/:child_id/status` (`status="archive"`; `"archived"` also accepted) | Primary parent + secondary parent (if set) |
| 6 | Admin assigns a new form to a student | `POST /student-form-assignments`, `POST /student-form-assignments/bulk`, `POST /student-form-assignments/school-wide`, `POST /student-form-assignments/class-wide` | Primary parent + secondary parent (if set) |

> Note on event 6 — the `add-child` flow (event 3) bulk-creates the initial enrollment forms but
> intentionally does **not** also send a per-form email; the child-added email already summarizes
> the form count. The form-assigned email only fires when forms are added to an *existing*
> enrollment.

## Architecture

- `EmailService` (Resend wrapper) is constructed once in `main.rs` as `Arc<EmailService>` and shared
  with `EnrollmentService` and `StudentFormAssignmentService` via constructor injection.
- Service methods perform their DB work first; on success they build a payload and dispatch the email
  on a detached `tokio::spawn`. Errors are logged but never propagated to the caller.
- Recipient resolution: primary parent comes from `users.email`; secondary parent (events 1, 2, 5)
  comes from `users.email` joined via `children.secondary_parent_id`. The `to:` field is
  comma-separated, which `EmailService` already splits and lowercases.
- Idempotency: none in-app. Resend handles its own retries.

## Visual design (shared shell)

All five templates render through a single helper `render_shell(accent, headline, preheader, body, cta)`
in `email_templates.rs`. This guarantees consistent header/footer, accent strip, max-width 600px,
single column, no remote images or JS, WCAG AA color contrast.

Palette:
- Slate `#2c3e50` (headings) / muted slate `#7f8c8d` (neutral accent)
- Blue `#3498db` (informational accent / CTA)
- Green `#27ae60` (success accent — Approved)
- Orange `#e67e22` (warning accent — Rejected, needs action)
- Background `#f9f9f9`, card `#ffffff`, border `#e0e0e0`

From: `Goddard Schools <no-reply@arjavatech.com>`
Reply-To: not set (parents are directed to contact their school admin via plain copy)
Plain-text fallback: auto-generated by Resend from the HTML

## Configuration

- `PARENT_DASHBOARD_URL` — base URL of the parent dashboard. Used to build CTA buttons.
  - **Dev:** `https://dev.goddard-app.pages.dev/` (also the in-code default when the env var is
    unset)
  - **Prod:** `https://goddardschool.org/` — must be set explicitly on the prod Lambda
    environment.

## Per-event details

### 1. Form approved
- Subject: `Good news! {form_name} has been approved for {child_name}`
- Accent: success green
- CTA: "Open Parent Dashboard" → `PARENT_DASHBOARD_URL`
- Notes block: rendered only when notes is non-empty

### 2. Form rejected (action required)
- Subject: `Action needed: {form_name} for {child_name} requires updates`
- Accent: warning orange
- CTA: "Update Form Now" → `PARENT_DASHBOARD_URL`
- Notes block: always rendered. Falls back to "Please contact your school administrator for details."
  when notes is empty.

### 3. Additional child added
- Subject: `{child_name} has been added to your Goddard School account`
- Accent: blue
- CTA: "Complete Enrollment Forms" → `PARENT_DASHBOARD_URL`

### 4. Parent account deactivated
- Subject: `Your Goddard School parent account has been deactivated`
- Accent: muted slate
- No CTA. Body directs the parent to contact their school admin.

### 5. Child archived
- Subject: `{child_name}'s record has been archived at {school_name}`
- Accent: muted slate
- No CTA. Body directs the parent to contact their school admin.

### 6. New form assigned
- Subject: `New form for {child_name}: please complete {form_name}`
- Accent: informational blue
- CTA: "Open Parent Dashboard" → `PARENT_DASHBOARD_URL`
- Details card includes: form name, child, school, required/optional, due date
  (from `form_templates.due_date`, falls back to "At your earliest convenience" when null),
  assigned-on timestamp.

## Service trigger points

| Event | File / function | When to fire |
|-------|-----------------|--------------|
| Form approved | `services/student_form_assignment_service.rs::review_student_form_assignment` | after DAO update success, when `request.status == Approved` |
| Form rejected | same | when `request.status == Rejected` |
| Child added | `services/enrollment_service.rs::add_child` | before returning the success response |
| Parent deactivated | `services/enrollment_service.rs::deactivate_parent` | after DAO success; parent email must be fetched first (DAO doesn't return it) |
| Child archived | `services/enrollment_service.rs::update_child_status` | after DAO success, when `request.status` (case-insensitive, trimmed) equals `"archive"` or `"archived"` |
| Form assigned | `services/student_form_assignment_service.rs::create_student_form_assignment`, `bulk_assign_forms`, `assign_form_to_school_students`, `assign_form_to_class_students` | once per newly created assignment, after DAO success |

## Manual test plan

1. **Form approved** — `POST /student-form-assignments/review` with `status=approved`; check Resend
   dashboard + inbox.
2. **Form rejected** — same endpoint with `status=rejected` and a sample `notes`.
3. **Add child** — `POST /enrollments/add-child`; confirm correct form count and classroom name.
4. **Deactivate parent** — `DELETE /parent/:parent_id`; confirm counts.
5. **Archive child** — `PATCH /children/:child_id/status` with `{"status": "archive"}` (the
   live frontend payload; `"archived"` also accepted); confirm one email. Then
   `{"status": "active"}` and confirm NO email.
6. **New form assigned (single)** — `POST /student-form-assignments` with a fresh
   `child_id`/`form_template_id`; confirm one form-assigned email to the parent(s) of that child.
7. **New form assigned (bulk)** — `POST /student-form-assignments/bulk`,
   `/student-form-assignments/school-wide`, or `/student-form-assignments/class-wide`; confirm one
   email per newly created assignment (none for skipped/duplicate students).
8. **Failure isolation** — set an invalid Resend key; confirm APIs still return 200 and errors are
   logged.

## Known limitations / out of scope

- Resend API key is hard-coded in `email_service.rs` (pre-existing). Not changed in this round.
- No `email_notifications` audit table; reliance on Resend dashboard for delivery status.
- No localization — English copy only.
- No per-school branding (logo, school name in header bar) yet.
